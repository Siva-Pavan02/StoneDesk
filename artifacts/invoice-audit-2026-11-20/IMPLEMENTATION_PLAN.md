# StoneDesk invoice accounting remediation

## Purpose and agreed policy

The release must prevent duplicate payments, hidden excess after invoice edits, fractional-paisa totals, lost payment history, and future invoices in current receivables. Independent decimal calculations must reconcile with the API, database, preview, PDF, dashboard, and payment insights.

For new and revised invoices, round each measurement row amount half up to paise, sum the rounded rows, then add the paise-valued loading/royalty fee. Remove the special `.75` whole-rupee rule. Keep old invoice and revision data unchanged. A revised invoice gets a new calculation version. Recorded payments are never deleted with an invoice. Future-dated invoices remain visible and labeled in lists, but are excluded from current invoice totals, counts, and receivables. Early payments count as received cash on their payment date. The buyer invoice PDF does not change when payments are made; payment details belong in a separate statement.

Tax, discounts, cancellation, refunds, and credit notes are outside this release. An organization-scoped payment request ID is independent of the same ID used by another organization.

## Detailed Implementation Plan

### 1. Exact money and versioned summaries

- Use `Prisma.Decimal` on the backend and the existing frontend `decimal.js`. Parse decimal inputs from their string representation; do not multiply currency with JavaScript floating-point values. For every regular, TOP, or unit row, compute exact billable quantity times rate, round half up to ₹0.01, then sum rounded row amounts. Quantize the fee to ₹0.01 before adding it. Reject payment and fee inputs with more than two decimal places rather than silently rounding them. Validate the same row rule in `loadMath.js`, the server calculator, the mock, and the A4 model.
- Store `calculationVersion: 2` in every newly calculated `summary`. Keep JSON money fields numeric for API compatibility, but convert to Number only after Decimal quantization, with `MONEY_MAX_PAISA = 1_000_000_000_000` (₹10 billion) and a `Number.isSafeInteger` cents check. For version 2, every monetary row amount, subtotal, fee, and total must be finite, nonnegative, within the limit, and have integral paise when parsed by Decimal from its JSON value. Reject invalid version-2 writes and fail visibly on invalid version-2 reads; never substitute zero or silently round. Absence of the marker means conceptual version 1.
- Add `billableAreaSqFt` as an exact decimal string on each new measurement row. Keep the existing rounded area field for current consumers. Show the exact area beside the rate and rounded row amount in preview and PDF. The A4 model uses rounded row amounts for version 2 and preserved stored amounts for version 1; historical PDFs continue to use each version's stored snapshot.
- New and revised summaries store an effective timestamp. Finalization records the first issue timestamp. Revision snapshots continue to preserve the prior inventory and summary and additionally record `revisedAt`, prior total, resulting total, payment status before, and payment status after. Existing snapshots are not backfilled.

### 2. Lock revision and deletion against payments

- In `reviseDispatch`, begin one transaction, lock the organization-scoped dispatch with `SELECT ... FOR UPDATE`, then check finalized status and the caller's `updatedAt`, validate the replacement fields, calculate the version-2 total, sum committed payments as Decimal, reject `newTotal < received` with `409`, append the revision snapshot, and update the dispatch before commit. Retain the existing saved-reference and audit behavior after commit.
- In `deleteDispatch`, lock the same organization-scoped dispatch inside one transaction, check role and current status, count payments inside the lock, and return `409` whenever a payment exists. Delete only the permitted dispatch. Remove the payment-row deletion path. The existing payment POST already locks this dispatch row, so these three writes serialize on one invoice.

### 3. Idempotent payment contract and schema

- Add `clientRequestId String?` to `InvoicePayment` in `schema.prisma`. Prepare one additive SQL file in `Backend/prisma/changes` that adds the nullable column and creates `CREATE UNIQUE INDEX "InvoicePayment_org_clientRequestId_key" ON "InvoicePayment" ("organizationId", "clientRequestId") WHERE "clientRequestId" IS NOT NULL;`. The index is managed by SQL because Prisma 6 cannot express a compound unique constraint with an optional field. Update the disposable database test harness to apply the SQL after `db push`; existing rows remain `NULL`.
- `POST /dispatches/:id/payments` requires a UUID `clientRequestId`. Missing or malformed IDs return `400` with a short refresh instruction. Normalize amount to a two-decimal Decimal and note by trimming and treating blank as `null`; reject amounts with fractional paise. The first successful insert returns `201` and `{invoiceTotal, received, balance, status, payments}`. A replay with the same organization, ID, dispatch, normalized amount, and note returns `200` with the same saved payment in `payments` and a freshly computed current summary. Reuse for a different invoice, amount, or note within the organization returns `409`. Another organization cannot see the first organization's key or invoice and may use the same UUID independently.
- Keep the dispatch row lock and check for an existing key before balance validation, so a retry after full payment succeeds as a replay. If a unique-index race occurs on different dispatches, roll back, re-read the winner by organization and key, then return `200` or `409` under the same comparison rule. Mirror all status codes and response shapes in the mock.
- `AddPaymentDialog` creates one UUID for a new submission and retains it and the submitted payload across network retries. After an uncertain response, changing amount or note first refreshes payment state; only a distinct new payment intent receives a new UUID. A newly opened dialog starts a new intent.

### 4. Future dates, paid events, and payment statement

- Use the existing Asia/Kolkata day-window helper to exclude dispatch dates after today from billed, outstanding, receivables, unpaid/partial/full counts, party balances, and all-time invoice analytics. Apply this cutoff to each invoice-derived SQL CTE and the mock equivalent. Do not apply it to receipt CTEs: early cash is counted by `InvoicePayment.createdAt`. Label future invoices in loading and invoice lists.
- For the period's `Invoices paid in full`, merge payments and amount-changing revisions in timestamp order. New revision snapshots provide prior/resulting totals and status transitions; version-1 snapshots derive those totals from adjacent stored summaries and `revisedAt`. Stable IDs/array order break timestamp ties. Count only invoices currently PAID, at their latest transition into PAID, no earlier than the invoice date. Exclude and report legacy records whose missing snapshot data makes the event time unprovable; never invent a timestamp. Keep the outstanding and receipt totals independently reconcilable.
- Add organization-scoped `GET /dispatches/:id/payment-statement`. Read the dispatch and payment rows in one Prisma `RepeatableRead` transaction and obtain `asOf` from that transaction's database timestamp. Return `{asOf, timeZone: 'Asia/Kolkata', invoice: {id, number, date, partyName, revisionNumber, calculationVersion, total}, payments: [{id, amount, note, createdAt, createdBy}], received, balance, status}`. Monetary values in this new response are decimal strings with two digits after the point. The route returns `404` for another organization's invoice.
- Add a payment statement export button that fetches this snapshot once per click and renders its PDF. Render the `asOf` timestamp in IST. Use a sanitized `Payment-Statement-<invoice-number>-<YYYYMMDD-HHmm-IST>.pdf` filename. The statement describes the current invoice revision and its complete payment ledger, without a historical revision timeline; historical invoice versions remain available through their separate PDFs. Payment actions do not change existing invoice PDFs.

### 5. Verification and rollout

- Add independent Decimal expectations before comparing UI, API, PostgreSQL, mock, and PDF results. Cover same-key replay, changed note/amount, cross-dispatch reuse, cross-organization isolation, missing/malformed IDs, concurrent identical requests, unique-index race, full and partial payment, excess rejection, upward and downward revisions, stale edits, payment/revision races, and paid deletion by every role. Test mixed regular/TOP/unit row rounding, exact area, ₹1,466.75, version-1 fractional totals, and version-2 validation failures.
- Cover future invoices visible in lists but absent from current/all-time invoice balances and counts; early cash remains in received and trend. Test a paid invoice reopened by an upward revision, then paid again, and confirm the latest completion event and current status. Test statement snapshot totals, all payment rows, IST `asOf`, sanitized filename, and unchanged current/historical invoice PDFs after payment. Restore mock receivables and a valid branding fixture.
- Inventory legacy fractional totals and excess payments read-only before rollout and report unresolved records separately. Run backend and frontend test suites, frontend build, and the end-to-end audit in a disposable database. On the same preview environment and fixed fixture, take 30 warmed `period=all` analytics samples before and after; post-change p95 must be no more than 20% higher. No-go if any new write duplicates a payment, creates excess, stores fractional paise, loses a payment row, or produces an accounting mismatch.
- Follow `Backend/prisma/MIGRATION.md`: prepare and review the additive SQL; before applying it to the intended database, obtain operator approval and a backup; apply SQL; generate Prisma Client; run `protectDatabase.js`; then deploy backend and frontend together. Do not use `migrate deploy` against the existing unbaselined database.
