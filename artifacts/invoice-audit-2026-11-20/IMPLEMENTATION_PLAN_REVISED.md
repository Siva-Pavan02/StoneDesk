# StoneDesk invoice accounting remediation — implementation plan

## Goal and accounting policy

Prevent duplicate payments, excess created by invoice edits, fractional-paisa totals, deletion of payment history, and future invoices in current receivables. Verify amounts against independent Decimal calculations across API, PostgreSQL, local UI, analytics, and PDFs.

For new invoices and revisions, compute each row from exact area or unit quantity times rate, round the row amount half up to paise, sum rounded rows, and add the fee. A net of ₹1,466.75 remains ₹1,466.75. Existing invoice data and revision snapshots are not rewritten. A buyer invoice PDF is a versioned invoice document and does not change when payments are recorded. A separate payment statement shows current payments and balance. Tax, discounts, cancellation, refunds, and credit notes are outside this release.

## Public contracts and invariants

### Money and revisions

- Version 2 is marked by `summary.calculationVersion === 2`. A missing marker means legacy version 1. `summary.baseMaterialTotal`, `loadingAndRoyaltyFees`, and `netBillableAmount`, plus each stored row/group `lineTotal`, remain JSON numbers for API compatibility. Create each only from a Decimal value rounded half up to two places. `MONEY_MAX_PAISA = 999_999_999_999` (₹9,999,999,999.99); reject values outside this range before Number conversion. Validate with Decimal that each version-2 stored value has integral paise, is finite and nonnegative, and is within range. JSON numbers may omit a trailing zero; scale is an arithmetic invariant, not a display-string invariant.
- For `measurementRows`, calculate one rounded amount per row from `lengthFt × widthFt × quantity × rate`. For legacy `pieces` input used in a new/revised version-2 invoice, calculate one rounded amount per piece from `lengthFt × widthFt × rate`; retain the pieces shape. For unit rows, use `quantity × rate`. `group.lineTotal` is the sum of its rounded row/piece amounts, `summary.baseMaterialTotal` is the sum of group amounts, and net is material plus a fee validated to integral paise. Add `billableAreaSqFt` as the exact decimal string used for each version-2 measurement row and piece. Keep the existing rounded `sqFt` fields for older consumers; preview and PDF show the exact billable area with its rate and rounded amount.
- New drafts have version-2 totals but no issue time. Finalization stores `summary.issuedAt` and `summary.effectiveAt` as the same UTC ISO timestamp obtained inside the write transaction. A revision retains `issuedAt` if known and sets the new summary's `effectiveAt` to its transaction timestamp. The appended prior-version snapshot keeps its existing data and gains `revisedAt` (same timestamp), `priorTotal`, `resultingTotal`, `paymentStatusBefore`, and `paymentStatusAfter`. Revising a legacy invoice creates a version-2 current summary but does not change older snapshots or invent an original `issuedAt`.
- On valid version-1 totals with fractional paisa, read paths round half up to paise for derived balances and display while preserving stored values and historical PDF totals. Preserve zero-total invoices' existing `PAID` status, but exclude them from the positive-value paid-completion KPI. For historical excess, expose `excess = max(received − rounded invoice total, 0)` while balance stays zero; do not erase or silently net it elsewhere.
- One backend validator checks all version-2 row, group, and summary money on draft create/update, finalize, and revise, and checks stored summaries before payment reads/writes, statement reads, invoice detail/list responses, receivables, and analytics. The mock applies the same rule. Invalid stored money returns HTTP `500` with `{error: 'Invoice amount needs review.'}` on a single-invoice route or `{error: 'Invoice totals need review.'}` on aggregate routes; the UI shows the error state, never zero figures. Server logs identify the affected invoice. Valid legacy fractional values are the only values rounded on read.

### Payment POST and statement GET

- Add `InvoicePayment.clientRequestId String? @db.Uuid`. A named, organization-scoped PostgreSQL partial unique index enforces non-null IDs. The SQL file uses `ADD COLUMN IF NOT EXISTS "clientRequestId" uuid` and `CREATE UNIQUE INDEX IF NOT EXISTS "InvoicePayment_org_clientRequestId_key" ON "InvoicePayment" ("organizationId", "clientRequestId") WHERE "clientRequestId" IS NOT NULL`, then verifies an existing column is UUID rather than accepting a mismatched type. `schema.prisma` declares the nullable field without `@@unique`. Existing rows remain `NULL`. The disposable test database setup applies this idempotent SQL after `prisma db push`, which has already created the column.
- `POST /dispatches/:id/payments` accepts `amount` as a JSON number, `clientRequestId` as a UUID string, and optional `note` as a string. Reject missing/malformed IDs with `400`. Parse `amount` through `Prisma.Decimal(String(amount))`, reject more than two decimal places before formatting, and retain the existing `0 < amount ≤ ₹10,000,000` cap. Trim `note`; blank becomes `null`. The first save returns `201` and the existing `{invoiceTotal, received, balance, status, payments}` body with additive `excess`. An identical replay returns `200` with the original payment row in `payments` and a freshly computed current summary. Compare organization, dispatch, normalized amount, and normalized note. Reuse on a different invoice, amount, or note in the same organization returns `409`. The same UUID in another organization is independent and reveals nothing about the first.
- Check the request ID after taking the dispatch row lock and before checking remaining balance, so a retry after full payment returns `200`. On a unique-index conflict between different dispatch rows, roll back and re-read by organization and ID, then return `200` or `409` under the same comparison. Old open clients without an ID receive a short `400` refresh instruction rather than an unprotected write. The mock matches the real statuses and response shapes.
- `GET /dispatches/:id/payment-statement` returns `404` for an invoice outside the session organization. It reads the dispatch, current version, and all payments in one `RepeatableRead` transaction; obtain `asOf` from the database transaction timestamp in that same snapshot. The `200` JSON is `{asOf, timeZone: 'Asia/Kolkata', invoice: {id, number, date, partyName, revisionNumber, calculationVersion, total}, payments: [{id, amount, note, createdAt, createdBy}], received, balance, excess, status}`. All monetary values in this new response are decimal strings with exactly two digits. `revisionNumber` is `revisions.length + 1`. The statement includes the current revision identity and complete payment ledger, without a historical revision timeline; old invoice versions remain separate PDFs.

### Analytics and dates

- Use the existing Asia/Kolkata day boundary. `all_finalized` includes every finalized invoice and supplies party identity for receipts. `eligible_finalized` adds `d.date < end_of_today_IST` and supplies billed, outstanding, unpaid/partial/full counts, receivables, and completed-invoice events. Receipt and trend CTEs join `all_finalized` and filter by `InvoicePayment.createdAt`, so early cash on future invoices remains received. The separate `/dispatches/receivables` query also applies the eligible date boundary. Loading/invoice lists still return future invoices; the frontend derives a `Future-dated` label from the invoice date in IST, with no new list field.
- Build paid-completion events by merging payment rows and amount-changing revision events. New snapshots contain prior/resulting totals and paid status. For legacy snapshots, derive the prior total from that snapshot's summary and the resulting total from the next snapshot's summary or the current summary; use the stored `revisedAt`. Sort by UTC timestamp, then revision before payment on equal timestamps, then revision array position or payment UUID. Final current status is authoritative. Only a currently `PAID` invoice with a positive total can contribute its latest transition to paid. If that transition precedes a future invoice date, assign the event to the invoice date's IST start and exclude it until that date. A revision without enough stored time or total to prove completion is omitted from the period completion count and added to `paymentAnalytics.excludedCompletionCount`; the UI labels that count as legacy dates requiring review. No timestamp is invented.

### Atomic revision and deletion protocol

- `PUT /dispatches/:id/revise` requires `updatedAt`; missing or malformed tokens return `400`, and a token that differs from the locked dispatch returns `409`. Within one Prisma transaction, select the organization-scoped dispatch `FOR UPDATE`, check finalized status and the stale token, validate fields, compute the new version-2 total, sum the committed `InvoicePayment.amount` values as Decimal, and return `409` if the proposed total is below receipts. Append the prior-version snapshot and update the dispatch before committing. The payment POST locks the same dispatch row, so payment and revision cannot pass conflicting checks concurrently.
- `DELETE /dispatches/:id` selects the organization-scoped dispatch `FOR UPDATE` in one transaction. Check current role and status, then the payment-row count under that lock. A non-admin deleting a finalized invoice receives `403` regardless of payment state. An admin deleting any invoice with one or more payment rows receives `409`, whether partially or fully paid. Any role deleting an anomalous draft with a payment row receives `409`. Only an authorized dispatch with zero payments is deleted; this path never deletes payment rows.

## Acceptance tests and release gate

**Accounting regressions.** Independently calculate expected values with Decimal before each comparison. Verify duplicate/changed-note/changed-amount/cross-invoice UUID cases, same UUID in another organization, unique-index races, partial/full/excess payments, zero totals, mandatory/missing/stale revision tokens, upward and downward revisions, and payment-versus-revision/delete races. Assert admin deletion fails for partially and fully paid invoices, non-admin finalized deletion returns `403`, and any draft payment blocks deletion. Verify row rounding for regular, TOP, unit, mixed, and pieces inventories; exact area; ₹1,466.75; and both valid legacy fractional values and invalid version-2 values. Check UI, API, PostgreSQL, mock, and PDF separately.

**Analytics and documents.** Verify future invoices appear in lists but not current or all-time invoice balances/counts; early cash appears in receipts and trend; an invoice reopened by an upward revision leaves the paid-completion KPI until paid again. Verify `excludedCompletionCount` on incomplete legacy event data. Check that payments never change current/historical invoice PDFs and that the statement matches its snapshot JSON, including excess and IST time.

**Latency.** On one preview environment and a fixed fixture, take 30 sequential warmed request-duration samples for `/api/dispatches/analytics?period=all` before and after. Sort each set and use the 29th value as nearest-rank p95. Post-change p95 must be at most 1.20 times baseline; investigate any failure before release.

**Legacy inventory and deployment.** The read-only audit script reports organization and invoice IDs, raw and rounded legacy totals, excess received, and incomplete revision-event reasons; do not commit production output. No-go if a new write duplicates payment, creates excess, stores fractional paisa, deletes payment history, or causes an accounting mismatch. Prepare and review additive SQL, obtain operator approval and a backup before applying it to the intended database, apply SQL, generate Prisma Client, run `protectDatabase.js`, and deploy backend and frontend together. Do not run `migrate deploy` against the unbaselined existing database.
